**先挑战三个前提**

1. “像现实中的建筑”不等于“逐栋复刻了真实城市”。对标作品源码大量使用建筑原型、退台、屋顶、立面参数和分区组合，当前没有证据证明所有楼都对应真实建筑。我们要同时追求建筑逻辑可信和深圳地标可辨认；只改随机高度/颜色，仍会单调。
2. “找照片并尽可能还原”不是一个简单循环。对象识别、视角与年代冲突、尺寸推断、体块关系和颜色校准都需要判断。单视图可以有多种三维解释，缺少背面资料时应记录估计或缩小范围，不能靠想象补成“精确还原”。
3. 更低的单次模型费用不一定更省。应比较“生成 + 重试 + Pro复核/返工”的总成本。无边界研究、反复读大仓库、十轮自评分和反复全城重建都可能吃掉节省的额度。可编写成确定性脚本的循环，不应每轮再让模型解释一遍。

**一、建筑多样性怎么做**

先按“地块/楼栋数 → 足印/朝向 → 体块与高低关系 → 退台/凹口/连桥/屋冠 → 首层与屋顶 → 材质分区 → 窗格/文字”推进。轮廓没成立时不做密集幕墙。灰模用来检查比例与体块，之后必须检查材质版和游戏实际光照。

| 层级 | 制作方式 | 第一批建议 | 验收重点 |
| --- | --- | --- | --- |
| 重点地标 | 逐栋查证、明确估计项，独立模型 | 精品路线内先选3–5个，不把清单中所有地点一起重做 | 遮掉招牌仍可凭轮廓辨认；朝向、数量、主次比例成立 |
| 常见城市建筑 | 制作可复用原型，加受约束的参数变体 | 先4类通过，再扩为8–12类 | 同类具有合理建筑逻辑，不同类有不同足印、楼顶、首层和材料 |
| 远景建筑群 | 保留城市布局和高度节奏，合并简化 | 为已完成样段的外围建立远景版本 | 远近切换不突兀，天际线保留，不能把所有细窗带进远景 |

普通楼首批可选：板式住宅、点式住宅、办公塔楼配裙楼、街边商业。扩展候选包括H/U形楼、阶梯塔楼、圆角塔楼、连桥双塔、院落商业和仓储建筑。每类先有明确结构，再做2–3个受约束变体；不要把随机形变称为风格多样。原型不是具名建筑的实景复原。

颜色也要按材料拆：玻璃、金属框、混凝土、石材、涂料分别记录。照片里的蓝玻璃可能主要反射蓝天，黄墙可能来自夕阳；不能直接把单张照片的像素色写为模型底色。优先两个不同日照条件下的照片，在固定中性光下校准固有色，再到游戏晴天/黄昏/夜间复核。夜景发光需要自己的观察依据。

**三、统一生产流水线与停机点**

| 阶段 | 必需输入 | 交付与通过条件 | 未通过时 |
| --- | --- | --- | --- |
| 资料 | 明确地点/楼座、现有来源和三个具体缺口 | 有来源的身份/定位；至少两个可判断形体的方向；尺寸区分reported/measured/estimated；保留冲突 | 继续交已有资料，列缺口；资料充分才可进入建模 |
| 规格 | 资料包、现有模型、项目坐标 | 体块清单、关键比例、至少3项辨识特征、材料分区、预算、固定验收视角；由集成人员冻结 | 只升级冲突项给Pro，已确认项不重复研究 |
| 灰模 | 冻结规格、B API样板 | 前/后/左/右/俯视/街面三分之四视角；塔楼数量、主次关系、朝向和轮廓一致 | 先改体块，不用窗格或反光掩盖比例问题 |
| 材质/细节 | 通过的灰模与来源 | 材质版同机位；结构、玻璃/实体墙、入口与屋顶层次；解释照片估计色 | 同一中性光下判断，不以“更亮/更饱和”为唯一改进 |
| 导出 | 候选模块、实际构建环境 | GLB、源码/输入/输出哈希、实读资源统计、构建命令、LOD与截图 | 没执行就写未执行；缺GPU/浏览器则交候选，不能称最终通过 |
| 集成 | 已审候选、替换ID与接入说明 | 旧楼排除、碰撞、游戏材质一致性和目标机器帧时间 | 集成人员修共享问题；资产作者只修自己的对象 |

`spec.md`与`review.md`是本手册补充的交付文件，不是现有CLI已实现的自动门槛。CLI仍只有 `planned → evidence-ready → modelled → verified`。语法/字段通过不代表照片支持主张；`verified`须具名证据，不能批量填pass。资料或模型变化后，复核受影响项。

补充人工检查：长度/高度必须有单位、合理正值和比例依据；CLI可能接受0或描述字符串，不能当成尺寸已经可信。`mixed_use_district`任务不会自动要求每栋高度/朝向，精修其中一栋时须在spec补齐。不能把核心未知项移到pending子范围后宣称整栋完成。当前三角面等预算只在verified阶段强检，候选交付也应提前实读检查。

每个任务默认先做一版 + 至多两次针对具体问题的修复；连续两次同类错误，或关键资料冲突，就停该问题并提交升级包，不启动无限循环。研究任务先限定三个缺口、约6–10张去重的有效参考；数量是上限建议，来源覆盖比凑图重要。参考图应按观察日光/背光/拍摄方向标注；无法判断写unknown。

**四、图像与数据交付格式**

在任务目录增加 `reference-index.md`：每行记录来源ID、原网页、发布方、访问日期、图片日期/未知、实拍/效果图/施工、拍摄方向/未知、对应楼座、支持哪个部件、访问失败项，以及用途。每条`evidence.json`观察引用来源ID，附事实或估计方法。图片仅作参考，许可允许的文件才进入可分发资产；不要把网上整幅照片直接作为立面贴图。

`spec.md`至少包含：

- 对象ID和本轮子范围；沿用的证据SHA256；楼座对应与可观察方向。
- 真实米制参数与误差范围、WGS84足印、朝向和高度基准；部件之间的相对关系。
- 三至五项关键识别特征与必须保持的结构，未获证据的背面如何简化。
- 几何/材质分区、通用原型或实景对象的身份、预算与LOD方案。
- 固定视角、灯光、画面尺寸；各项怎么判通过；集成人员确认记录。

`review.md`只写有证据的差异：参考来源/候选截图、对应结构、差异、影响、下一次只修什么。透视差异未配准时不要用像素重合率伪装几何精度。图片不同角度应比较可见的结构关系，不能要求逐像素一致。

**五、预算、坐标和文件所有权**

每栋/紧凑楼群默认继承现有任务上限：25,000三角形、12材质、8 MiB GLB、贴图边长2048；这是候选资产上限，不是必须用满或3060性能保证。增加预算需由集成人员结合实际同屏成本调整。材质数不等于draw calls，阴影和反射会重复绘制。普通原型应更便宜。不要因3060目标就全城增加高模。

坐标与B API必须读现有契约：WGS84原点`[114.025,22.536]`，东西乘102850、南北乘111320，水平与竖直统一缩放0.60一次；GCJ-02/BD-09不能直接混用。Blender东/北/上由现有导出/运行时处理轴向。不要在普通Python导入`city_mesh.py`，它会初始化Blender场景。

B API两个易错点：`box`的位置是中心；`footprint(mat,ring,z,h)`的`h`是顶部绝对Z，不是从z起算的增量。按实际源码核对封闭环、法线和材质名。腾讯模块的lm.x/z已是游戏坐标，spec尺寸仍是真实米，不能二次缩放位置。

每个对象一个写入者，尽量使用独立候选目录。已有财富广场、七街公馆、万象天地共用`priority.py`，外部Agent不得并行改该文件。需要修改总构建器、public资产、排除ID、运行时、共享材质时，写`integration-notes.md`给集成人员。当前目录有未提交游戏工作；不要执行reset、clean或覆盖他人文件。后续若使用工作树，先由集成人员固定可用基线，不让执行者自行假定远程main就是当前资产。

**七、如何实际节省Pro用量**

首轮先做小型资格试验：同一份冻结规格、同一预算、同一组图分别给两个模型各一次，比较通过率、修复轮数、总用量和Pro复核时间，再决定哪类任务固定交给谁。模型只需要读自身job、规格、B API和一个样板；不要每次都附9分钟视频、完整聊天或整城几百MB资产。

基础规则通过链接复用，不复制成长系统提示。Cursor支持项目规则与AGENTS.md，可按需引用本手册；不需要为本次任务另改用户全局规则。[Cursor规则说明](https://cursor.com/docs/rules)。

运行已有脚本、等待Blender、批量截图、统计哈希等流程一次实现后直接执行。Pro的介入点压缩到：规格首次确认、轮廓关卡、冲突/反复失败、最终游戏集成；普通交付由另一个执行者初审。不要让Pro持续轮询每张图或把外部执行者的整段日志重新总结。

每批保留一行统计：`taskId / 执行模型与环境 / 输入版本 / 结果 / 修复次数 / 实际用量(未知则空) / Pro复核分钟 / 剩余问题`。目标是降低“每个通过验收资产”的总成本，不预先承诺节省百分比。
